## 1. Per-unit summary

- **S1 CONFIG (R3)**: `prototype/js/CONFIG.js` `CONFIG.assets.caster`: 3 new rows,
  `castShotSpeed: 1.5`, `fire1HFraction: 0.46`, `cast1HClipSeconds: 2.3`, each with

  No other CONFIG change. Cast2H has no fraction row.
- **S2 anim.js (R1 + R4)**:
  - `CharacterAnim.prototype.castShot` (anim.js:283): after `transition(shot, ...)`
    resolves (`this.clip === shot`), the Cast1H action gets
    `timeScale = CASTER().castShotSpeed` (1.5). It is set once per start and never
    reset to 1. `transition()` does not touch timeScale (three.js `reset()` keeps
    it), and the next state change `.stop()`s or fades the action. Cast2H's action
    is never written, so it stays at timeScale 1.
  - `this.castShotKey`: set to `shot` when the shot starts, or when the repeat guard
    finds the same shot still running. It is set to `null` on every refusal (dead,
    `attackPhase`, missing clip) and if the transition did not land.
  - `CharacterAnim.prototype.endCastShot` (anim.js:295): clears `castShotKey`.
    Otherwise unchanged.
- **S3 player.js (R2 + R5)**:
  - `Player.prototype.tryCast` (player.js:1460): after the existing
    `c.windup = castWindup` and `anim.castShot(...)`, the windup is extended when
    all of these hold: `!this.casterMode`, `role === 'main'`, the spell kind is
    `'projectile'`, and `anim.castShotKey === 'Cast1H'`. The extension is
    `c.windup = Math.max(0, c.windup, fire1HFraction * cast1HClipSeconds / castShotSpeed)`
    = max(0.25, 0.46·2.3/1.5 = 0.7053) ≈ **0.705 s**. The brief rounds this to
    0.71 s; the exact pinned-fraction value 0.4638 gives 0.711 s.
  - The windup clock itself is not new: tickCasts, completeCast and the game.js
    spawn loop are unchanged. The Cast2H (casterMode) path keeps the V7
    castWindup exactly.
  - `Player.prototype.castProgress` (player.js:1527): the return value is clamped
    to [0, 1]. While the windup is above castWindup the glow pulse reads 0, then it
    ramps over the final castWindup seconds as before.

## 8. Deviations + reasons
- **No code deviations.** R1-R7 are implemented as ruled.
- **Doc 65 was untracked at bcbb227.** Appending the section and listing it in the
  commit therefore adds the whole file (70 prior lines + the new section). This
  was not edited beyond the append.
- **Factual note on R1 (no code impact).** In the vendored three.js
  (three.classic.js:54432/54483), a LoopOnce + clampWhenFinished action sets
  `paused = true` when it finishes. `isRunning()` then returns **false**, not
  true. So `castShotRunning()` drops when the clip ends and syncPlayer crossfades
  back to locomotion. The clamp-weight table (`self.clip === key && CAST_SHOTS`)
  holds the pose only through that crossfade. This is the bcbb227 behaviour,
  unchanged. At 1.5x the shot ends about 1.53 s after accept instead of 2.3 s.
  The bolt (0.705 s) fires well inside the running shot.
- **Factual note on R7 weave casts (no code impact).** castShot refuses while
  `attackPhase` is set. A cast accepted during an attack windup therefore plays
  no shot, `castShotKey` is null, and the windup stays at the native castWindup
  0.25 s. It is not extended. This is intended by R4: no visible wind-up motion
  means no stretch.
